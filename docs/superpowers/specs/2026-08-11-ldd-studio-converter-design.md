# LDD → Studio 模型转换工具 设计文档

日期：2026-08-11
状态：已确认设计，待实现

## 1. 背景与目标

LEGO Digital Designer（LDD）和 Studio 2.0 是两套独立的乐高建模软件，使用不同的零件编号体系和颜色体系。用户需要一套工具，将 LDD 工程（`.lxf`）修复后交给 Studio 导入，解决零件变问号、零件乱飞、自定义颜色无法识别、BOM 不准确的问题。

**交付物：** Windows 桌面 GUI 工具，读取 `.lxf` → 修复 → 输出干净 `.lxf`，由 Studio 自带导入功能打开。

## 2. 需求清单

| # | 需求 | 说明 |
|---|------|------|
| R1 | 自定义颜色互通 | LDD 官方 palette 机制的自定义颜色，能在 Studio 识别 |
| R2 | 自定义零件互通 | LDD 中的自定义/官方零件在 Studio 中不变成问号、不乱飞 |
| R3 | 零件映射修复 | LDD DesignID → Studio（BrickLink）编号，2000+ 需修复 |
| R4 | BOM 准确 | 转换正确后由 Studio 导出 BOM，零件名/颜色名全对 |
| R5 | 未匹配不猜 | 找不到精确对应的零件保留原 ID，列入报告，不近似替换 |

## 3. 技术栈

- Python 3.11+
- PySide6（GUI）
- lxml（LXFML XML 解析）
- SQLite（映射数据库，标准库）
- PyInstaller（打包 Windows 单文件 exe）

## 4. 架构

单进程桌面应用，四模块解耦，GUI 不直接碰数据格式：

```
┌─────────────────────────────────────────────┐
│  GUI（PySide6）                               │
│  工程选择 → 修复 → 报告查看 → 输出             │
├──────────────┬──────────────────────────────┤
│  LXF 解析器   │  映射引擎（核心）               │
│  zip+xml 读写│  读公开数据 + 本机库 → 映射表    │
├──────────────┼──────────────────────────────┤
│  颜色处理器   │  零件处理器                     │
│  自定义色转换│  designID→BL 编号 + 矩阵修复     │
└──────────────┴──────────────────────────────┘
```

### 4.1 LXF 解析器

- `.lxf` 是 ZIP 容器，内含 `p1.xml`（LXFML）和缩略图目录
- 负责解压、解析 LXFML、写入修正结果、重新打包
- 对每个 `<Brick>` 读取：`designID`、`materialID`、`transform`（3x4 矩阵）、子零件层级 `refID`
- 保持文件内其他内容（Meta、缩略图、未涉及属性）不变

### 4.2 映射引擎（核心）

首次运行流程（`build_mapping_db`）：

1. 扫描 LDD 安装目录：零件库 XML（约 6000 个零件）、palette 自定义颜色定义
2. 扫描 Studio 安装目录：零件库（BL 编号）、颜色 XML
3. 合并公开数据集（Rebrickable / BrickLink DesignID→BL 映射）
4. 三方交叉比对，生成 SQLite 映射库：
   - `parts` 表：`design_id`、`bl_number`、`name`、`match_type`（exact/auto/manual）
   - `colors` 表：`ldd_color_id`、`bl_color_id`、`rgb`、`name`、`is_custom`
5. 本地缓存，后续启动跳过重建

未匹配零件可在 GUI 报告页手动指定，写入映射库（`match_type=manual`）。

### 4.3 颜色处理器

- **官方色**：`ldd_color_id` → `bl_color_id` 直接映射
- **自定义色**（R1）：从 LDD palette 提取 RGBA + 名称 → 检查 Studio 是否已有 → 没有则写入 Studio 自定义颜色 XML 并引用；`.lxf` 内 `materialID` 替换为新颜色 ID

### 4.4 零件处理器

- **编号替换**（R3）：`designID` 查映射表 → 换成 Studio 认识的 BL 编号
- **乱飞修复**（R2）：识别乱飞根因并修正：
  - 子零件映射失败导致父级 `refID` 引用断裂 → 子件修复后父级自动恢复
  - 两软件零件几何中心不同（带枢轴/铰链的零件）→ 从本机库读两软件各自原点数据，计算偏移量并补偿 transform
- **未匹配**（R5）：保留原 ID，写入报告

## 5. 数据流

1. **首次运行**：扫描两软件安装目录 → 合并公开数据 → 生成 SQLite 映射库
2. **转换时**：读 `.lxf` → 逐 Brick 处理（编号/颜色/矩阵）→ 写回修正 LXFML → 重新打包
3. **输出**：修正后 `.lxf` + 修复报告（替换记录、未匹配清单、自定义色清单）

## 6. GUI 设计（3 个页面）

### 6.1 转换页
- 选择 `.lxf` 文件
- 配置：修复乱飞 / 写自定义色 / 输出目录
- 转换按钮 + 进度条 + 完成提示

### 6.2 报告页
- 三个 Tab：替换记录 / 未匹配 / 自定义色
- 未匹配项右键"手动指定"，选择 Studio 零件，保存进映射库

### 6.3 映射库页
- 浏览全部零件映射（6000+），搜索
- 批量编辑，导出/导入映射表（CSV）

## 7. 错误处理

- 找不到 LDD/Studio 安装目录 → 引导用户手动指定路径，映射库降级为"仅公开数据"模式
- 单个 Brick 解析失败 → 跳过并记录到报告，不中断整体转换
- 自定义色写入 Studio 失败 → 报告警告，颜色用最近官方色兜底（报告标明）

## 8. 测试策略

使用用户提供的真实 `.lxf`（含自定义颜色/零件）作为回归测试集。每个样例断言：

1. 零件数转换前后一致
2. 每个零件要么映射成功，要么出现在未匹配报告中（无静默错误）
3. 自定义颜色 RGBA 转换前后一致
4. Studio 打开输出文件无问号、无乱飞
5. Studio 导出 BOM 零件名/颜色名正确
